# S2R Review — 소스·운영 취약점 검증

S2R은 **Source to Runtime**의 약자입니다. 소스코드에서 만든 취약점 가설을 운영 환경의 제한된 검증까지 연결합니다.

FastAPI·Flask·Django·Express·Next.js·NestJS·Spring Boot·Laravel 프로젝트의 소스를 읽고 기술 취약점 후보를 검토하는 한국어 로컬 앱입니다. 기본 선택지에 FastAPI 실습 서비스 **TechLab**과 Spring Boot 실습 서비스 **ReleaseHub**가 있습니다. 새 분석은 AI 전용입니다. 게이트웨이에 연결한 모델(예: Nemotron)이 Python AST·Tree-sitter 구문 단서와 원본 함수 본문을 함께 읽고 엔드포인트와 취약점 시나리오를 제안합니다. 앱은 제안된 파일·줄·경로의 근거를 확인하고, 운영 요청 안전성·생성 코드·수정 diff를 독립적으로 검사합니다. 이전 규칙 기반 분석 결과는 이력에서 열람할 수 있습니다.

**현재 정식 분석 대상은 위 8개 웹 프레임워크입니다.** 폴더 선택은 프레임워크가 아니라 의존성 파일과 소스 확장자를 먼저 확인하므로 다른 프레임워크 프로젝트도 선택될 수 있습니다. 다만 읽는 애플리케이션 소스는 Python·JavaScript/TypeScript·Java·PHP 확장자로 한정됩니다. AI 결과 검증은 위 8개 프레임워크의 엔드포인트만 인정하며, 그 밖의 라우트 제안은 제외되거나 분석이 실패할 수 있습니다. 지원 프레임워크에서도 모든 라우트 발견이나 자동 운영 검증을 보장하지는 않습니다.

S2R Review: <http://127.0.0.1:8020/> · TechLab: <http://127.0.0.1:8010/> · ReleaseHub: <http://127.0.0.1:8030/>

## 기본 실습 프로젝트

TechLab은 가상의 소프트웨어 아티팩트 카탈로그입니다. 사용자·주문·권한 흐름 없이 다음 네 가지 기술 취약점을 각각 한 경로에 담았습니다. 서비스 데이터는 실습용으로 고정되어 있습니다. 아래 응답은 검증 계획의 예시입니다. TechLab의 예시 경로는 모두 GET이며, 앱은 선택한 메서드·경로와 AI 진단 입력을 별도 검사한 뒤 시나리오당 최대 두 번 요청합니다.

| 시나리오 | 경로 | 소스에서 찾는 근거 | 추가로 검토할 응답 |
|---|---|---|---|
| SQL 삽입 | `GET /api/products?q=` | 검색어를 SQL 문자열에 직접 삽입 | 검색어 두 개의 결과 개수 차이 |
| 반사형 XSS | `GET /search/preview?q=` | 입력을 HTML에 이스케이프 없이 삽입 | 무해한 HTML 태그의 원문 반사 |
| 경로 순회 | `GET /api/files?name=` | 공개 폴더보다 넓은 상위 폴더로 경계 검사 | 실습용 비공개 마커 노출 여부 |
| 외부 리다이렉트 | `GET /go?next=` | 입력 URL을 `RedirectResponse`에 직접 전달 | 외부 `.invalid` URL을 가리키는 `Location` 헤더 |

경로 순회 샘플은 앱에 포함된 합성 데이터 폴더 안에서만 동작하며 다른 호스트 파일로의 접근은 거부합니다. SQL 조회 연결은 읽기 전용입니다. TechLab은 `127.0.0.1`에만 바인딩합니다. 샘플 자체의 실행·테스트 방법은 [TechLab README](../samples/techlab/README.md)에 있습니다.

## 사용하기

1. **TechLab** 또는 **ReleaseHub (Spring Boot)**를 선택하거나 **폴더 선택**으로 지원 프레임워크의 소스 프로젝트를 연결합니다. ReleaseHub는 최상위 `NemoClaw` 폴더에서 PowerShell의 `samples/start-spring-releasehub-preview.ps1` 또는 Linux/WSL Bash의 `samples/start-spring-releasehub-preview.sh`로 `127.0.0.1:8030`에서 실행합니다. 선별된 소스 내용과 구조 단서는 연결된 모델 제공자로 전송됩니다.
2. **분석 시작**을 누릅니다. 앱이 선별한 원본 파일을 작업별 OpenShell 샌드박스의 `/source`에 각각 읽기 전용으로 마운트하고, OpenShell 파일 정책으로 해당 입력 영역만 허용한 뒤 실제 접근 경계를 검사합니다. AST·구문 트리는 함수·호출 위치를 탐색하는 데 쓰고, 모델이 표시된 함수 본문과 연결 가능한 보조 함수를 읽어 엔드포인트·입력값·기술 취약점 가설을 만듭니다. 두 번째 AI 검토는 입력 한도에 들어오는 최대 8개의 미검토 엔드포인트를 대상으로 라우트, 함수 본문, 관련 선언과 연결 가능한 보조 함수를 제시해 보호 검사와 반례를 다시 따집니다. 정해진 취약 함수명이나 사용 지점 키워드로 시나리오를 생성하거나 걸러내지 않습니다. 앱은 모델이 인용한 실제 소스 줄과 엔드포인트 연결을 확인하지만 데이터 흐름의 의미적 정확성까지 증명하지는 않습니다. 첫 모델 호출이나 필수 응답 형식·라우트 근거 검증에 실패하면 작업을 실패로 기록합니다. 일부 근거 불일치 제안은 제외하고 계속하며, 첫 검토의 시나리오 근거가 모두 맞지 않으면 해당 제안을 제외하고 두 번째 검토를 시도합니다. 재검토의 보호 검사 설명을 검증하지 못해도 별도로 소스 근거가 확인된 시나리오는 남기고 평가 미완료를 표시합니다. 파싱·생략 현황은 **분석 범위·한계**에서 확인할 수 있습니다.
3. **02 시나리오 선택**에서 취약점 카테고리로 목록을 필터링하고, 카테고리 안의 시나리오를 모두 선택하거나 해제할 수 있습니다. 시나리오마다 카테고리가 분석 기록에 저장됩니다. 요청할 엔드포인트/메서드는 오른쪽에서 별도로 고릅니다. 각 항목에 코드 위치, 위험 가설, 진단 방법과 해석 한계가 표시됩니다. 필요한 엔드포인트를 제외하면 그 시나리오는 실행할 수 없습니다. 선택을 저장합니다.
4. **03 운영 검증**에서 본인이 관리하는 테스트 서버의 origin을 입력하고 검증을 실행합니다. 호스트는 소스 분석에서 선택한 입력의 위치를 쿼리 또는 JSON 본문으로 정합니다. 모델은 선택된 시나리오의 함수 코드와 위험 가설을 보고 그 위치에 넣을 기준값·후보값과 두 응답을 비교하는 Python 판정 함수를 제안합니다. 앱은 선택한 엔드포인트의 메서드·리터럴 경로·입력과 원본 함수의 근거를 독립적으로 확인한 뒤 시나리오마다 최대 두 요청을 보냅니다. HTTP 메서드와 관계없이 요청은 대상의 상태를 바꿀 수 있으므로 테스트 환경에서 실행해야 합니다. 같은 불변 소스 분석에서 앞서 검증된 AI 계획은 재검증한 뒤 재사용합니다. 자동 요청 부적격이거나 AI 입력 쌍을 검증하지 못한 항목은 요청 없이 오프라인 검토로 기록합니다. OpenShell 정책 적용·요청 실행·정책 복원에 실패하면 운영 점검 작업을 실패로 기록합니다. 호스트는 진단 입력과 Python AST를 검증하고 요청 코드를 제한된 템플릿으로 구성합니다. 오프라인 판정의 본문 문자열은 제공된 함수 코드의 실제 문자열 리터럴과 대조해, 소스에 없는 파일 내용 등을 추측한 판정을 거부합니다. 자동 요청이 불허된 경우에도 검증된 오프라인 Python 스크립트를 제공할 수 있습니다. 생성이나 검증이 실패하면 이유를 기록하고 실행 스크립트를 제공하지 않습니다.
5. **04 조치방안**에서 모델이 취약 지점의 실제 함수 코드와 운영 결과를 바탕으로 제안한 시나리오당 한 파일의 수정 diff를 확인합니다. 워커는 원본과 수정안을 비교하는 별도 AI 검토를 거쳐 잔존 위험이 지적되면 한 번 재수정합니다. 호스트는 변경 전 줄·파일 해시·수정 범위를 검사하고 Python 변경안은 문법도 검사한 뒤 diff를 만듭니다. 삭제 줄은 빨강, 추가 줄은 초록입니다. 근거가 부족하거나 검토에서 효과를 확인하지 못하면 이유만 표시합니다. 표시된 diff도 안전성 증명이 아니므로 사람이 검토해야 하며, 원본 파일은 자동 수정하지 않습니다.
6. **05 통합 리포트**에서 선택 범위, 실제 요청 메서드·경로, 응답 판정과 조치방안을 내려받습니다. 생성 코드가 검증된 시나리오에는 개별 Python 스크립트를 제공합니다. 통합 `check.py`에는 운영 요청이 승인되고 실제 관찰된 항목만 들어가며, 다른 항목의 개별 스크립트는 사용자가 준비한 응답을 오프라인으로 검토합니다. 자동 운영 요청이 없었던 스크립트는 자동 점검 성공의 증거가 아닙니다.

별도 버튼으로 PyPI·npm·Maven(POM·Gradle)·Packagist 패키지의 정확한 고정 버전을 OSV에서 조회할 수 있습니다. **버튼을 누르면 해당 패키지 이름과 버전이 외부 OSV 서비스로 전송됩니다.** 공지가 발견되면 **수동 검토** 항목이 추가됩니다. 이 항목은 함수 코드에서 AI가 생성한 취약점 가설과 구분되는 패키지 공지 조회 결과입니다. 공지의 존재만으로 배포본의 영향이나 악용 가능성을 확정하지 않습니다.

운영 판정의 `취약 동작 관찰`은 AI가 제안한 두 입력과 제한된 HTTP 응답을 비교한 결과입니다. SQL 검색 차이, 파일 응답, 외부 `Location`, 비실행 HTML 태그 반사 등은 선택된 시나리오에서 자동으로 관찰될 수 있습니다. 응답 차이만으로 취약성을 확정하지 않으며, XSS 태그 반사는 브라우저에서 스크립트가 실행됐다는 증거가 아닙니다. 소스 흐름·예상된 정상 동작·배포 설정을 함께 검토해야 합니다.

## 실행과 갱신

설치 스크립트는 Windows·WSL Ubuntu·Docker Desktop의 OpenShell 게이트웨이를 전제로 합니다. WSL 배포판, OpenShell CLI 경로 또는 게이트웨이 이름이 다르면 `review/bridge.py`와 `setup_worker.py`의 설정을 환경에 맞게 조정해야 합니다. Docker Desktop, WSL, 게이트웨이가 실행 중이어야 하며 AI 분석에는 게이트웨이의 모델 제공자 설정이 필요합니다.

원본 파일의 bind mount를 사용하려면 게이트웨이 설정의 `[openshell.drivers.docker]`에서 `enable_bind_mounts = true`를 활성화하고 게이트웨이를 재시작해야 합니다. 이 설정은 게이트웨이 전체에 적용되므로 샌드박스 생성 권한은 신뢰할 수 있는 호스트 제어기에만 주어야 합니다. [OpenShell 0.0.116 마운트 설명](https://docs.nvidia.com/openshell/v0.0.116/reference/sandbox-compute-drivers)도 호스트 bind mount가 격리를 약화할 수 있다고 경고합니다.

Windows PowerShell의 `s2r-review` 폴더에서 처음 준비할 때:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -B setup_worker.py --update
```

그다음 저장소 최상위 폴더에서 샘플 서비스와 앱을 시작합니다:

```powershell
.\samples\start-techlab-preview.ps1
.\s2r-review\start.ps1
```

앱 서버는 창 없이 실행됩니다. 저장소 최상위 폴더에서는 `.\s2r-review\stop.ps1`로 중지합니다. 저장된 프로세스 ID·시작 시각·명령행이 일치하는 앱 프로세스만 종료하며 분석 이력과 샌드박스는 보존합니다.

WSL 또는 Git Bash에서는 저장소 최상위 폴더에서 Bash 스크립트로 같은 Windows 호스트 앱을 시작·중지할 수 있습니다. 위에서 준비한 Windows용 Python 가상환경을 사용하며, WSL의 Linux Python으로 앱을 직접 실행하는 구성은 아닙니다.

```bash
# 시작
bash s2r-review/start.sh
# 종료할 때
bash s2r-review/stop.sh
```

Linux/WSL에서 샘플 서비스도 Bash로 실행할 수 있습니다. TechLab에는 별도의 Linux용 Python 가상환경이 필요하며, 준비 방법은 [TechLab README](../samples/techlab/README.md)에 있습니다. ReleaseHub에는 Java 17 이상이 필요합니다.

```bash
bash samples/start-techlab-preview.sh
# 필요할 때: bash samples/stop-techlab-preview.sh
bash samples/start-spring-releasehub-preview.sh
# 필요할 때: bash samples/stop-spring-releasehub-preview.sh
```

워커 소스를 수정한 뒤에는 진행 중인 작업을 마치고 `s2r-review` 폴더에서 `.\.venv\Scripts\python.exe -B setup_worker.py --update`를 실행합니다. 이 옵션은 기준 워커의 Python 소스를 교체하고 새 작업용 이미지를 갱신합니다. 이미 생성된 작업별 샌드박스의 이미지는 바뀌지 않으므로, 워커가 변경된 뒤에는 해당 분석의 결과를 열람할 수는 있지만 운영 점검을 다시 하려면 새 분석을 시작해야 합니다. Tree-sitter 등 네이티브 파서 패키지의 버전이 바뀌면 새 이미지의 샌드박스를 준비해야 하며, 설치 도구는 현재 패키지 버전이 선언값과 다르면 코드만 갱신하지 않습니다. 설치 도구가 전용 워커 코드의 체크섬·파일 경계와 파서 버전을 확인합니다. 호스트 앱 코드를 수정했다면 앱 서버도 재시작합니다.

## NemoClaw / OpenShell 경계

```text
브라우저 UI / Windows 호스트 앱
  └─ 선별한 파일 목록과 분석 시점 SHA-256 기록
      └─ 작업별 OpenShell 샌드박스
          ├─ /source  선별된 원본 파일 각각 읽기 전용 마운트 · Landlock 읽기 허용
          ├─ /input  초기 분석 매니페스트, 후속 AI 작업 입력과 승인된 운영 요청 설정
          ├─ Python AST·Tree-sitter 구문 트리 → 모델 입력용 구조 단서 수집
          ├─ inference.local → 모델이 함수 코드를 읽고 엔드포인트·취약점 시나리오·Python 점검 계획·수정 줄 제안
          ├─ 호스트 검증 → 소스 인용·진단 입력·Python AST·수정 원본 줄 확인
          ├─ 임시 OpenShell 정책 → 선택한 서버·메서드·리터럴 경로만 허용
          └─ /output → 호스트에서 파일·줄 근거 검증 후 결과 저장
```

S2R Review는 NemoClaw용 OpenShell 게이트웨이에 연결하는 **별도 OpenShell 워커**입니다. Python의 `ast`는 Python 소스의 추상 구문 트리를, Tree-sitter는 해당 언어의 구문 트리를 만듭니다. 둘은 같은 자료형이 아닙니다. 워커는 파싱 가능한 범위에서 구조 단서를 추출하고, 큰 파일에서는 가능한 한 완전한 함수·선언 본문을 모델에 제시합니다. 모델이 엔드포인트 식별, 함수 흐름을 바탕으로 한 기술 취약점 가설, 시나리오별 Python 점검 계획, 소스별 수정 줄을 제안합니다. 구문 트리만으로 라우트나 취약점을 확정하지 않습니다. 앱은 소스 근거 확인, 사용자 선택, 실행 안전성, OpenShell 정책 적용과 생성 코드·수정안 검증을 담당합니다. 모델은 사용자가 고른 서버나 파일 접근 범위를 바꿀 수 없습니다. 분석 대상의 코드를 import·빌드·실행하지 않고 소스만 읽습니다.

새 분석은 선택한 프로젝트에서 선별된 원본 파일만 작업별 샌드박스에 각각 읽기 전용으로 마운트합니다. 평가용 정답 폴더와 다른 프로젝트는 마운트하지 않습니다. 초기 소스 분석에서는 호스트 제어기가 선별 파일의 경로·해시만 `/input`에 전달하고, 워커가 `/source`의 허용 파일을 직접 읽어 시작 시점 해시와 대조합니다. 후속 점검·조치 단계에서는 시나리오·함수 코드·운영 요청 설정도 별도 `/input` 파일로 전달합니다. 소스 본문은 분석 기록 `bundle.json`에도 저장되어 결과 검증과 이후 수정 diff에 사용됩니다. 호스트 제어기는 OpenShell 샌드박스 UUID, Docker 컨테이너 ID와 실제 마운트를 대조하며, 워커에는 Docker 소켓을 제공하지 않습니다.

Landlock `hard_requirement` 정책에서 선별 파일만 있는 `/source`와 `/input`, `/app`은 읽기 전용, `/output`, `/tmp`, `/dev/null`은 쓰기 가능 영역입니다. 시스템 실행에 필요한 라이브러리·설정 경로도 읽을 수 있습니다. 기본 네트워크 정책은 Python의 `inference.local:443` `POST /v1/chat/completions`만 허용합니다. API 키를 분석 코드에 넣지 않습니다. 매 분석 전에 허용 소스 읽기와 쓰기 거부, 동일한 원본 파일을 정책 밖 경로에 연결했을 때의 읽기 거부, `/input` 쓰기 거부와 `/output` 쓰기를 실제 파일 열기로 확인합니다. 이 시험은 설정한 경계의 동작 확인이지 모든 보안 속성의 증명은 아닙니다.

운영 검증 시 앱은 원본 소스의 라우트·처리 함수 위치와 사용자가 선택한 엔드포인트·메서드·입력을 확인합니다. 승인된 요청에만 선택 서버·리터럴 경로·메서드의 임시 `runtime_target` 정책을 만들고, OpenShell이 보고한 정책을 대조한 뒤 **시나리오당 기준값·후보값 각 한 번, 최대 두 요청**을 보냅니다. 두 입력은 같은 메서드·경로·입력 이름과 위치를 사용하고 값만 다릅니다. 쿼리 입력은 URL 인코딩하고 본문 입력은 단일 필드 JSON으로 보내며 본문은 최대 512바이트입니다. 요청값의 문자 범위를 검사하고 쿠키·인증 정보는 보내지 않으며 리다이렉트를 따르지 않습니다. 응답 본문은 요청마다 최대 64 KiB로 제한하고 임시 관찰 파일을 읽은 후 호스트에서 삭제합니다. 최종 결과에는 본문을 저장하지 않습니다. 실행 뒤 기본 네트워크 정책을 복원·확인합니다. 복원에 실패하면 작업별 샌드박스를 삭제하거나 정확한 컨테이너를 중지하고, 앱 재시작 때도 중단된 임시 정책을 복구·격리합니다. **메서드·경로 제한과 코드 검사는 연결된 보조 함수, 미들웨어, 배포 프록시의 부작용을 완전히 증명하지 못합니다. 특히 상태 변경 메서드는 실제 데이터를 바꿀 수 있습니다.** 자동 요청 부적격·AI 계획 미검증 시나리오는 오프라인 검토로 남지만, OpenShell 정책·실행·복원 오류는 운영 점검 실패로 기록됩니다.

완료된 분석의 작업별 샌드박스는 같은 분석에서 운영 점검을 다시 실행할 수 있도록 남겨 둡니다. 분석을 여러 번 반복하면 읽기 전용 원본 마운트가 붙은 컨테이너도 누적되며 현재 자동 만료 기능은 없습니다. 필요 없는 작업별 샌드박스는 OpenShell에서 해당 분석의 이름과 UUID를 확인해 정리하고, 같은 소스를 다시 점검하려면 새 분석을 시작하세요. 저장된 보고서·스크립트·diff 파일은 호스트에 계속 남습니다.

Python 스크립트 생성 요청에는 시나리오에 인용된 함수 코드·위험 가설·메서드·경로가 포함되지만 운영 대상 서버 주소, 실제 응답 본문, 인증 정보는 보내지 않습니다. 모델은 자동 요청 대상일 때 같은 입력 이름·위치의 기준값·후보값과 두 응답을 비교하는 순수 `evaluate(response)` 함수를 작성합니다. 자동 실행 대상이 아니면 진단 입력을 비워 두고 오프라인 관찰값만 판정하는 함수를 작성합니다. 호스트는 입력값, Python AST, 응답 필드 접근과 반환 형식을 검사하고 선택된 메서드·경로로 보내는 제한된 요청 코드를 스크립트에 조립합니다. 내려받은 Python 파일은 사용자가 직접 검토하는 용도입니다. 샌드박스 밖에서 실행하면 OpenShell 정책은 적용되지 않으며 대상 상태를 바꿀 수 있습니다. 오프라인 스크립트는 서버에 요청하지 않습니다.

공식 참고(OpenShell 0.0.116): [OpenShell 정책](https://docs.nvidia.com/openshell/v0.0.116/reference/policy-schema), [관리형 추론 경로](https://docs.nvidia.com/openshell/v0.0.116/sandboxes/inference-routing).

## 저장과 지원 범위

기본 저장 위치는 `s2r-review` 폴더와 나란한 `../s2r-review-data/jobs/<작업 UUID>/`입니다. `S2R_REVIEW_DATA` 환경 변수로 데이터 루트를 바꿀 수 있습니다.

| 파일 | 내용 |
|---|---|
| `status.json`, `events.jsonl` | 작업 상태·시각·단계별 실행 기록 |
| `bundle.json` | 선별된 소스의 분석 시점 복사본 |
| `result.json`, `report.md` | 엔드포인트·코드 근거·AI 분석 내용·분석 보고서. JSON의 `ai.syntax_assist`에는 구문 구조 단서의 파싱·생략 현황 기록 |
| `selection.json`, `scenarios.json` | 선택 버전과 근거가 확인된 시나리오 |
| `dependency-audit.json` | 선택적으로 조회한 OSV 공지 |
| `runs/<운영 점검 UUID>/` | 관찰 결과·정확한 허용 범위·통합 보고서·생성에 성공한 Python 스크립트와 생성 상태. AI 계획·패치 입력 및 대상 origin·선택 경로·진단 값이 든 운영 입력 JSON도 보존 |

소스 비교 해시는 선별된 UTF-8 파일의 경로와 내용에 대한 SHA-256입니다. 전체 폴더나 제외 파일을 검증한 해시가 아닙니다. 호스트의 소스 복사본과 결과는 자동 삭제하지 않습니다. 새 분석은 작업별 샌드박스로 분리되지만, 단일 사용자 로컬 개발용 구성이고 사용자 인증·권한 분리는 제공하지 않습니다. `.env`, 숨김 폴더, 실행 데이터, 일부 민감 파일명과 링크 파일을 제외하지만, 일반 소스 안에 하드코딩된 비밀값을 완전히 제거하지는 못합니다. 분석을 시작하기 전에 모델로 전송할 코드 내용을 확인하세요.

- 지원하는 프로젝트 루트에는 Python 의존성 파일, `package.json`, `pom.xml`·`build.gradle`, `composer.json` 중 하나가 필요합니다. 최대 245개 파일, 파일당 200 KB, 총 3 MB의 UTF-8 텍스트를 읽습니다. AI 모드에서는 이 범위 안의 소스·줄 번호와 제한된 양의 구조 단서를 모델에 제공하고 엔드포인트·시나리오의 코드 근거를 요구합니다. 구조 단서의 파싱 성공·실패, 건너뛴 파일, 모델 입력에 포함되거나 제외된 단서 수는 `result.json`의 `ai.syntax_assist`에 기록합니다.
- 구문 트리 수집은 선택한 소스의 보조 분석입니다. 파싱에 실패하거나, 지원하지 않는 파일 또는 입력 길이 제한으로 구조 단서가 빠질 수 있습니다. 수집 수치는 전체 프로젝트의 코드 경로나 엔드포인트 검출률을 뜻하지 않습니다.
- AI가 제안한 엔드포인트와 시나리오를 파일·줄 근거에 연결하지만, 그 사실만으로 라우트 등록 여부, 데이터 흐름, 실제 취약 여부를 완전히 증명하지는 못합니다. 동적 등록·복잡한 별칭·전역 미들웨어·프레임워크별 확장 기능은 누락될 수 있습니다.
- 새 분석은 AI만 사용하며 이전 규칙 기반 분석은 이력 열람용으로 보존합니다. AI는 XSS·SQL 삽입·경로 탐색·오픈 리다이렉트 외의 기술 취약점 카테고리도 제안할 수 있습니다. 카테고리는 목록 구분용이며 취약점의 존재를 확정하는 판정이 아닙니다. 정해진 코드 키워드 표로 후보를 생성하거나 필터링하지 않습니다. 자동 요청은 별도 실행 경계를 통과한 선택 엔드포인트의 메서드·리터럴 경로에만 허용되며 기준값·후보값 두 요청을 비교합니다.
- OSV 조회는 PyPI·npm·Maven·Packagist의 직접 선언된 정확한 고정 버전에 한정됩니다. 사용자 지정 저장소·URL·범위·변수 버전은 전송하지 않고 미확인으로 표시합니다. 매니페스트만으로 개별 패키지가 실제로 공개인지 증명할 수는 없으므로 조회 전 패키지 이름을 확인하세요.
- AI의 엔드포인트 식별과 취약점 가설에는 2차 재검토 후에도 누락·오해가 있을 수 있습니다. 2차 검토는 1차에서 확인한 엔드포인트 중 입력 한도에 들어오는 최대 8개를 대상으로 하며 독립적인 엔드포인트 발견을 수행하지 않습니다. 첫 AI 호출이나 필수 형식·라우트 근거 검증이 실패하면 작업 오류를 보여 줍니다. 일부 근거 불일치 제안은 제외하고 계속하며, 첫 시나리오 근거가 전부 틀리면 해당 제안 없이 2차 검토를 시도합니다. 2차 검토가 실패하면 첫 분석 결과에 경고와 한계를 표시합니다. 이전에 완료된 분석 기록은 보존됩니다.
- 앱은 한 번에 한 작업만 실행합니다. 앱 재시작 시 진행 중이던 작업은 중단으로 기록됩니다.

`s2r-review` 폴더에서 실행합니다.

```powershell
.\.venv\Scripts\python.exe -B -m pytest -q
```

이 테스트는 AI 제안의 소스 근거 검증, 선택 범위·보고서 저장, 자동 요청 경계, 생성 Python 코드와 수정 diff의 호스트 검증, OpenShell 정책 복원 경로 등을 확인합니다. 샘플 서비스 자체의 테스트는 [TechLab README](../samples/techlab/README.md)를 참고하세요.
